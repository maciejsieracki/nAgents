# MVP1 — Spięcie

**Cel: pracownik loguje się firmowym kontem, widzi wyłącznie agentów, do których ma prawo,
i rozmawia z nimi. Każde użycie jest zapisane, każdy model wywołany przez naszą bramę.**

Wycena: **10–12 dni roboczych.** Zakres: jeden agent projektowy (księgowość),
2–3 użytkowników, jedna instancja Hermesa.

---

## 1. Co wchodzi w zakres

| # | Element | Opis |
|---|---|---|
| 1 | Szkielet aplikacji | FastAPI, Postgres, migracje, konfiguracja przez zmienne środowiskowe |
| 2 | Logowanie przez Entra ID | OIDC, sesja w podpisanym ciasteczku, wylogowanie |
| 3 | Rejestr agentów | tabele `agent`, `agent_grant`; wypełniany z pliku YAML |
| 4 | Silnik uprawnień | funkcja `can_use(user, agent)`, domyślna odmowa, 404 zamiast 403 |
| 5 | Lista agentów | ekran z agentami widocznymi dla zalogowanego |
| 6 | Ekran rozmowy | wysyłanie wiadomości, strumieniowanie odpowiedzi |
| 7 | Proxy do Hermesa | przekazanie rozmowy do właściwego profilu, mapowanie sesji |
| 8 | Brama modeli | LiteLLM, klucz wirtualny na agenta, miesięczny limit |
| 9 | Audyt | zapis operacji dozwolonych i odrzuconych |
| 10 | Rejestr zużycia | tokeny i koszt przypisane do agenta i użytkownika |
| 11 | Provisioner | polecenie wystawiające profil Hermesa z rejestru |
| 12 | Wdrożenie | Docker Compose, TLS, kopia bazy raz na dobę |

## 2. Co świadomie zostaje poza zakresem

- Panel administracyjny — zarządzanie przez plik rejestru i polecenia (MVP2)
- Synchronizacja grup z katalogu — nadania wpisywane ręcznie (MVP2)
- Wspólna pamięć między agentami — **zablokowane do czasu rozstrzygnięcia rezydencji danych**
- Kanał w Teams — dostęp przez przeglądarkę (MVP3)
- Rutyny i harmonogramy (MVP3)
- Agenci stanowiskowi — w MVP1 tylko projektowi (MVP2/MVP3)
- Tokenizacja danych wrażliwych (MVP4)

## 3. Ekrany

| Ścieżka | Ekran | Uwagi |
|---|---|---|
| `/login` | przycisk „Zaloguj kontem firmowym" | bez formularza hasła — nie mamy haseł |
| `/agents` | lista dostępnych agentów | nazwa, opis, ostatnie użycie |
| `/agents/{slug}` | rozmowa | historia, pole wiadomości, strumień odpowiedzi |
| `/admin/audit` | dziennik zdarzeń | wyłącznie dla roli `owner`; filtr po decyzji |
| `/healthz` | stan usługi | bez uwierzytelnienia, bez danych |

Pięć ekranów. Dlatego szablony serwerowe zamiast osobnego frontendu.

## 4. API

```
GET  /                          → 302 na /agents albo /login
GET  /login                     → start OIDC
GET  /auth/callback             → wymiana kodu, utworzenie sesji
POST /logout                    → skasowanie sesji

GET  /agents                    → lista widocznych agentów
GET  /agents/{slug}             → ekran rozmowy (404 gdy brak uprawnień)
POST /agents/{slug}/messages    → wysłanie wiadomości
GET  /agents/{slug}/stream      → SSE z odpowiedzią

GET  /admin/audit               → dziennik (rola owner)
GET  /healthz  /readyz          → stan
```

**Każdy punkt wejścia z `{slug}` sprawdza uprawnienia niezależnie.** Brak sprawdzenia
w którymkolwiek to błąd krytyczny, nie usterka.

## 5. Przepływ rozmowy

```
1. Pracownik otwiera /agents/ksiegowosc
2. can_use(user, agent)?
   ├─ nie  → audit(deny, "brak nadania") → 404
   └─ tak  → audit(allow) → render ekranu
3. Pracownik wysyła wiadomość
4. Ponowne can_use — sesja mogła wygasnąć, nadanie mogło zostać cofnięte
5. Proxy → endpoint profilu Hermesa (nagłówek z identyfikatorem użytkownika
   i identyfikatorem żądania)
6. Hermes → brama modeli, kluczem wirtualnym agenta
   ├─ budżet przekroczony → brama odrzuca → komunikat dla użytkownika
   └─ w limicie → odpowiedź modelu
7. Hermes → strumień odpowiedzi → pracownik
8. Po zakończeniu: usage_event(agent, user, model, tokeny, koszt)
```

**Uwaga projektowa:** identyfikator żądania przechodzi przez wszystkie warstwy.
Bez niego nie da się później powiązać wpisu w audycie z kosztem i z sesją Hermesa.

## 6. Funkcja uprawnień

```python
def can_use(user, agent) -> tuple[bool, str]:
    """Domyślna odmowa. Zwraca (decyzja, powód) — powód idzie do audytu."""
    if not agent.is_active:
        return False, "agent nieaktywny"
    if not user.is_active:
        return False, "konto nieaktywne"
    if grant_exists(agent.id, "user", user.id):
        return True, "nadanie bezpośrednie"
    for group_id in user_group_ids(user):
        if grant_exists(agent.id, "group", group_id):
            return True, "nadanie przez grupę"
    return False, "brak nadania"
```

Nadania cofnięte (`revoked_at IS NOT NULL`) nie liczą się. Sprawdzenie jest jedno,
w jednym miejscu, wywoływane wszędzie.

## 7. Rejestr agentów — format

Plik `registry/agents.yaml`, wczytywany do bazy przez provisioner.
Rejestr jest w gicie, więc każda zmiana uprawnień to commit z autorem i datą.

```yaml
tenant: naster

agents:
  - slug: ksiegowosc
    nazwa: "Agent księgowości"
    opis: "Rozliczenia, prowizje, podkładki dla audytorów"
    rodzaj: projektowy
    hermes_profile: ksiegowosc
    model_default: <model tani, interaktywny>
    model_fallback: <model mocny, analizy>
    budget_monthly_usd: 200
    grants:
      - typ: group
        entra: "Księgowość"        # rozwijane do object id przy provisioningu
        rola: user
      - typ: user
        upn: "wlasciciel@naster.pl"
        rola: owner
    secrets:
      - nazwa: SYSTEM_ROZLICZEN_TOKEN
        vault_ref: "env:KSIEGOWOSC_ROZLICZENIA_TOKEN"
```

W MVP1 pole `entra` mapujemy ręcznie na identyfikator grupy. Automatyczna
synchronizacja wchodzi w MVP2.

## 8. Provisioner

```
nagents registry validate   # sprawdzenie składni i spójności, bez zmian
nagents registry apply      # rejestr → baza; pokazuje różnicę i pyta o potwierdzenie
nagents agent provision <slug>   # utworzenie profilu Hermesa + klucza w bramie
nagents agent revoke <slug>      # dezaktywacja: klucz unieważniony, dostęp odebrany
```

`apply` jest idempotentne — dwukrotne uruchomienie nie zmienia stanu.
Zawsze pokazuje różnicę przed zapisem; **nigdy nie modyfikuje uprawnień bez potwierdzenia.**

## 9. Wdrożenie

```yaml
# docker-compose.yml — MVP1, jeden serwer
services:
  caddy:     # TLS, reverse proxy
  nagents:   # FastAPI
  postgres:  # baza + wolumen
  litellm:   # brama modeli
  hermes:    # bramka Hermesa, tryb zwielokrotniony
```

**Zasoby wyjściowe:** 4 vCPU, 8 GB RAM, 100 GB dysku. Punkt startowy dla jednego
agenta i kilku użytkowników; sizing weryfikujemy po pierwszym tygodniu.

**Kopia zapasowa:** `pg_dump` raz na dobę + eksport profili Hermesa.
**Odtworzenie musi zostać przećwiczone przed uznaniem etapu za zamknięty** —
kopia, której nie odtworzono, nie jest kopią.

## 10. Scenariusze odbioru

Warunek zamknięcia etapu: wszystkie przechodzą, sprawdzone ręcznie na `prod`.

| # | Scenariusz | Oczekiwany wynik |
|---|---|---|
| 1 | Pracownik z grupy Księgowość loguje się | Widzi agenta księgowości, rozmawia z nim |
| 2 | Pracownik spoza grupy otwiera `/agents/ksiegowosc` | 404. W audycie wpis `deny` |
| 3 | Ten sam pracownik uderza w `/agents/ksiegowosc/messages` z pominięciem UI | 404. W audycie wpis `deny` |
| 4 | Konto wyłączone w Entra ID | Logowanie nieudane |
| 5 | Nadanie cofnięte w trakcie trwającej sesji | Kolejna wiadomość odrzucona |
| 6 | Wyczerpanie budżetu agenta | Brama odrzuca, użytkownik dostaje czytelny komunikat, nie błąd techniczny |
| 7 | Dodanie drugiego agenta | Wpis w rejestrze + `apply` + `provision`, poniżej pięciu minut |
| 8 | Rozmowa o rzeczywistym rozliczeniu | Wynik zgodny co do złotówki z liczeniem ręcznym |
| 9 | Odtworzenie bazy z kopii | System wraca do stanu sprzed, audyt kompletny |
| 10 | Przegląd audytu po dniu pracy | Widać kto, kiedy, do którego agenta, ile to kosztowało |

**Scenariusz 8 jest kryterium biznesowym całego etapu.** Reszta to warunki techniczne.

## 12. Ryzyka etapu

| Ryzyko | Skutek | Reakcja |
|---|---|---|
| Rejestracja aplikacji w Entra ID wymaga uprawnień administratora | Blokada od pierwszego dnia | Załatwić przed startem — to jedyna zależność zewnętrzna |
| Interfejs Hermesa do proxy okaże się inny niż zakładam | Utrata 1–2 dni | Sprawdzić w dniu pierwszym, nie siódmym |
| Model tani okaże się za słaby do rozliczeń | Scenariusz 8 nie przechodzi | `model_fallback` w rejestrze od początku |
| Kuszenie, żeby dołożyć funkcję z MVP2 | Etap się rozjeżdża | Wszystko poza listą z punktu 1 idzie do `decisions.md`, nie do kodu |
