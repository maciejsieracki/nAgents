# MVP4 — Skala

**Cel: system staje u nowego klienta bez dotykania kodu, wyłącznie przez konfigurację.
Dane wrażliwe nie opuszczają firmy w postaci jawnej.**

Wycena: **20–25 dni roboczych.**

| # | Element | Opis |

## 2. Tokenizacja — i czego nie załatwia

Warstwa podmieniająca identyfikatory przed wysłaniem promptu do modelu:

```
"Prowizja dla PPE 590310600012345678, umowa NAS/2024/1187"
            ↓ tokenizacja
"Prowizja dla PPE ⟨PPE_a7f3⟩, umowa ⟨UM_2c91⟩"
            ↓ model
"Prowizja dla ⟨PPE_a7f3⟩ wynosi 1240,50 zł"
            ↓ detokenizacja
"Prowizja dla PPE 590310600012345678 wynosi 1240,50 zł"
```

Tablica mapowania zostaje po naszej stronie, w bazie, nigdy nie opuszcza firmy.

> **Sprostowanie prawne, którego nie wolno pominąć:** to jest **pseudonimizacja**,
> a nie anonimizacja. Dane pseudonimizowane **pozostają danymi osobowymi** w rozumieniu
> RODO i nie zwalniają z obowiązków administratora. Anonimizacja zwalnia, ale wymaga
> nieodwracalnego usunięcia drogi do identyfikacji — przy rozliczeniach, gdzie wynik
> musi wrócić do konkretnej umowy, jest z definicji niemożliwa.
>
> **Wniosek: tokenizuj, bo realnie ogranicza szkodę przy wycieku — ale umowę
> powierzenia z dostawcą modelu podpisz mimo to.**

Wzorce konfigurowalne, bo numer PPE i numer umowy nie są standardowymi wzorcami,
które rozpozna gotowy filtr numerów identyfikacyjnych.

## 3. Pula instancji

```
              ┌─ nAgents ─┐
              │  routing  │  klucz: identyfikator sesji → instancja
              └─────┬─────┘
        ┌───────────┼───────────┐
   Hermes A     Hermes B     Hermes C
   profile      profile      profile
   1–10         11–20        21–27
```

- przypisanie sesji do instancji przez konsekwentne haszowanie
- awaria instancji → profile przenoszone, sesje odtwarzane z magazynu
- profil ma jednego pisarza — dwa procesy na tym samym profilu uszkadzają stan
- skalowanie: dodanie instancji zmienia przypisanie części profili, nie wszystkich

## 4. Router w Teams

Jeden bot `@Firma`. Pracownik pisze, router rozpoznaje intencję i przekazuje
do właściwego agenta — **sprawdzając po drodze uprawnienia pytającego**.

```
Pracownik: @Firma ile prowizji za maj dla Kowalskiego?
Router:    intencja → domena księgowość
           can_use(pracownik, agent_ksiegowosc)?
           ├─ nie  → "Nie mam do tego dostępu" + wpis deny
           └─ tak  → przekazanie, odpowiedź w wątku
```

Wchodzi dopiero teraz, bo wcześniej nie wiadomo, czy ludzie będą używać Teamsa
i które intencje faktycznie padają. Router zbudowany na domysłach rozpoznaje
niewłaściwe rzeczy.

## 5. Wielonajemność

Przygotowana od MVP1 przez `tenant_id` w każdej tabeli. W MVP4 domykamy:

| Element | Wymóg |
|---|---|
| Izolacja danych | każde zapytanie filtrowane po najemcy — wymuszone w warstwie dostępu, nie w kodzie zapytań |
| Izolacja profili | osobne katalogi, osobne klucze bramy, osobne workspace'y pamięci |
| Konfiguracja | jeden plik: nazwa, dzierżawa Entra, grupy, agenci, limity |
| Instalacja | `nagents tenant init <plik>` — bez dotykania kodu |
| Kopie zapasowe | per najemca, odtwarzalne niezależnie |

**Test odbioru:** postawienie systemu dla fikcyjnego drugiego klienta w jeden dzień,
przez osobę, która nie pisała kodu.

## 6. Bramka akcji

Wzorzec przejęty z projektów, które robią to dobrze: **każda operacja narzędzia
przechodzi przez sprawdzenie polityki przed wykonaniem.**

```
agent chce wykonać akcję
   ↓
bramka: czy istnieje reguła zezwalająca?
   ├─ nie → blokada + wpis w audycie (co próbował, dlaczego odmówiono)
   └─ tak → wykonanie + wpis w audycie
```

Domyślna odmowa. Audyt rejestruje **także próby odrzucone** — rejestr tego, co się udało,
mówi połowę prawdy; ciekawsze jest to, czego ktoś próbował i nie mógł.

## 7. Retencja i prawa osób

| Element | Rozwiązanie |
|---|---|
| Retencja rozmów | konfigurowalna per najemca, domyślnie 12 miesięcy |
| Retencja audytu | dłuższa niż rozmów — audyt to dowód, nie treść |
| Prawo do usunięcia | usunięcie rozmów i pamięci prywatnej osoby; audyt zostaje w formie zanonimizowanej |
| Eksport danych osoby | wszystkie rozmowy i pamięć prywatna w formacie tekstowym |
| Tablica tokenizacji | usuwana razem z danymi źródłowymi |

## 8. Scenariusze odbioru

| # | Scenariusz | Oczekiwany wynik |
|---|---|---|
| 1 | Pytanie z numerem PPE | W ruchu do dostawcy modelu wyłącznie token; odpowiedź poprawna |
| 2 | Awaria jednej instancji Hermesa | Rozmowy przenoszone, sesje odtworzone, użytkownik widzi zająknięcie, nie błąd |
| 3 | Pytanie do routera bez uprawnień | Odmowa, bez ujawnienia istnienia agenta |
| 4 | Instalacja dla drugiego klienta | Jeden dzień, wyłącznie konfiguracja, przez osobę spoza projektu |
| 5 | Próba akcji bez reguły zezwalającej | Blokada, wpis w audycie z opisem próby |
| 6 | Żądanie usunięcia danych osoby | Rozmowy i pamięć prywatna usunięte, audyt zanonimizowany, raport z operacji |
| 7 | Eksport danych osoby | Kompletny, czytelny, w formacie tekstowym |

## 9. Ryzyka etapu

| Ryzyko | Reakcja |
|---|---|
| Tokenizacja psuje kontekst i pogarsza odpowiedzi | Testy agenta z MVP3 uruchamiane przed i po; wzorce zawężane, nie poszerzane |
| Router rozpoznaje intencje niepewnie | Wariant awaryjny: pytanie zwrotne „chodzi o rozliczenia czy o umowę?" zamiast zgadywania |
| Wielonajemność okazuje się przedwczesna | Wydzielić jako osobny etap, jeśli nie ma drugiego klienta w perspektywie |
| Konektory do ERP okazują się największą pozycją | Wyceniać osobno, po jednym; nie wchodzą w cenę etapu |
